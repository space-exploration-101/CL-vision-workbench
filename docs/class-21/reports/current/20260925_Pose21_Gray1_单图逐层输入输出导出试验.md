## 1. 试验目的与结论

本次试验面向 FPGA 下游调试：固定一张 Gray1 图片和正式 weight-only ONNX，导出该图片经过网络时各 FPGA 计算层及路由节点的输入、输出，使下游能够按 `T32_Lxx_sxx` 层号与软件参考结果逐层比较。

这不是重新训练、重新量化或精度评估，也不会修改原始 ONNX。它回答的是“同一张图片在每一层产生了什么数值”，不回答“模型在整个数据集上的识别精度是多少”。

## 2. 使用的数据与网络权重

### 2.1 单张输入图片

本次使用量化标定集 `pose21_gray1_50e_cal462_v1` 中的一张图片：

```text
/data3/ywang/quantitize-platform/data/shared_data/cali/
pose21_gray1_50e_cal462_v1/cali/agaier_047_view_18.png
```

| 属性 | 值 |
|---|---|
| 文件名 | `agaier_047_view_18.png` |
| 文件大小 | 733,394 bytes |
| SHA-256 | `66b6416fef733d15b020adfdd2a543b58532da9eb294aaf230f3717967cb21dc` |
| 预处理模式 | `passthrough` |
| 网络输入 | `[1,1,1280,1280]` FLOAT16 |
| 归一化 | `pixel / 255.0` |

`passthrough` 表示保持单通道图片已经存储的灰度强度，不再执行 BGR 到 Gray 的加权转换。图片经过 resize、归一化和 NCHW 排列后进入网络。结果包同时保存原图 `source/source_image.png` 和 T32 排列后的 `source/network_input.bin`。

#### 2.1.1 从 PNG 得到 ONNX 逻辑输入

源文件已经是 `1280×1280、8-bit grayscale、non-interlaced PNG`，不是彩色图，也不是相机接口的原始 `cam1280` 数据。本次 `passthrough` 预处理按以下顺序执行：

```text
agaier_047_view_18.png
  1280 x 1280, uint8, 单通道
        |
        | 1. 以 IMREAD_UNCHANGED 解码 PNG
        | 2. passthrough：直接保留这个灰度平面
        | 3. INTER_LINEAR resize 到 1280 x 1280
        | 4. 转 FLOAT32，并除以 255.0
        | 5. 增加 channel 和 batch 维，排列为 NCHW
        | 6. 转为 FLOAT16
        v
ONNX 逻辑输入 images
  [1,1,1280,1280], FLOAT16
```

尽管这张图片已经是 `1280×1280`，公共预处理函数仍会调用一次 OpenCV `INTER_LINEAR` resize；在本例中目标尺寸与源尺寸相同。`passthrough` 的关键含义是“不重新计算灰度”，而不是“完全不做 resize、归一化和维度转换”。

归一化公式为：

```text
network_value = uint8_pixel / 255.0
```

因此 ONNX Runtime 实际接收的是归一化后的 FP16 数值，不是 0～255 的 uint8 字节。该逻辑 tensor 如果按紧凑 NCHW 直接保存，大小应为：

```text
1 x 1 x 1280 x 1280 x 2 bytes
= 3,276,800 bytes
= 3,200 KiB
= 3.125 MiB
```

这份紧凑数组在内存中直接作为 `{ "images": input_data }` 送入 ONNX Runtime。当前结果目录没有另外保存紧凑版 NCHW BIN；`source/network_input.bin` 保存的是下一步转换后的 FPGA T32 物理布局。

#### 2.1.2 从 ONNX 逻辑输入得到 `network_input.bin`

为了让 FPGA 网络第一层能够按 32-lane 通道并行格式直接读取，工具把逻辑通道数从 1 补齐到 32，再把通道移到最内层：

```text
逻辑输入： [1,1,1280,1280]       NCHW FP16
通道补齐： [1,32,1280,1280]      lane 0 有效，lane 1..31 补零
物理排列： [1,1280,1280,32]      T32_CHW32 FP16
                   |
                   v
source/network_input.bin
```

通用变换公式是：

```text
[1,C,H,W] -> [ceil(C/32),H,W,32]
```

本例 `C=1`，所以物理文件包含 32 个 lane，但只有每个像素位置的 lane 0 保存真实归一化灰度值，lane 1～31 必须全部为零。文件按 C-order 连续写入 little-endian FP16，不包含文件头、shape 或其他元数据；shape 和 dtype 必须从 `manifest.json` 获取。

`network_input.bin` 的实际合同为：

| 属性 | 值 |
|---|---|
| manifest tensor ID | `tensor_0000` |
| ONNX tensor 名 | `images` |
| 逻辑 shape | `[1,1,1280,1280]` |
| 物理 shape | `[1,1280,1280,32]` |
| 布局 | `T32_CHW32` |
| dtype | little-endian FP16 |
| 有效/补齐通道 | 1 / 31 |
| 文件大小 | 104,857,600 bytes = 102,400 KiB = 100 MiB |
| SHA-256 | `17e22501b3e0e9c6fd4435c982ab151a971367337eba9ab8435fbd85a7187765` |
| 数值范围 | min `0.0`，max `0.93701171875`，mean `0.20539890229701996` |
| NaN / Inf | 0 / 0 |

文件管理器显示的 `102400 KB` 实际采用的是 1024 进制的 KiB 口径。其大小计算如下：

```text
1 x 1280 x 1280 x 32 x 2 bytes
= 104,857,600 bytes
= 102,400 KiB
= 100 MiB
```

它恰好是紧凑单通道 FP16 输入的 32 倍；新增的 31 倍空间全部用于 T32 零填充。可按以下方式读取和检查：

```python
import numpy as np

physical = np.fromfile("network_input.bin", dtype="<f2")
physical = physical.reshape(1, 1280, 1280, 32)

gray = physical[0, :, :, 0]       # 实际 Gray1 网络输入
padding = physical[0, :, :, 1:]   # 应全部等于 0
assert np.all(padding == 0)
```

#### 2.1.3 与 `cam1280` 的边界

`network_input.bin` 是已经完成 PNG 解码、Gray1 确认、resize、`/255.0` 归一化、FP16 转换和 T32 排列后，准备直接进入 FPGA 神经网络第一层的数据。它不是 FPGA 图像预处理模块接收的相机原始 `cam1280` 数据。

两者关系如下：

```text
相机原始 cam1280
        |
        | 相机像素解析及项目约定的图像预处理
        v
Gray1 1280 x 1280 网络逻辑输入
        |
        | /255.0、FP16、T32 通道排列
        v
network_input.bin
        |
        v
FPGA 神经网络第一层
```

本次 `network_input.bin` 用于绕过相机采集和前处理链路，单独验证 FPGA 神经网络计算与 ONNX 软件 golden reference 是否一致。它不能用于证明 `cam1280 -> Gray1 网络输入` 这一段的像素位宽、字节打包、缩放、裁剪或其他相机预处理已经正确；该段需要使用正式 `cam1280` 测试向量另行验收。

### 3.1 核心定位

`export_layer_trace.py` 是一个“单张图片、正式 ONNX、FPGA 网络层边界的软件参考数据生成器”。它的核心任务是：

> 用显式指定的一张图片执行显式指定的 ONNX 模型，把 FPGA 各层应当收到的输入和应当产生的输出导出为可逐层比较的 T32 BIN，并同时生成足以解释这些 BIN 的层表、shape、dtype、布局和哈希清单。

其整体数据流为：

```text
指定 Gray1 PNG
      |
      | passthrough、resize、/255.0、NCHW、FP16
      v
ONNX 逻辑输入 [1,1,1280,1280]
      |
      | ONNX Runtime CPU 推理
      v
各 FPGA 层边界的逻辑 tensor
      |
      | 通道补零、T32 重排、小端 FP16 写盘
      v
network_input.bin + tensors/*.bin
      |
      v
manifest.json + layers.csv + SHA256SUMS
```

这些文件是软件侧 golden reference。下游可以将同一张图片送入 FPGA，然后依次比较 FPGA 的 `L00`、`L01`、`L02` 等层输出与本工具生成的对应 BIN。第一个出现不可接受差异的层，就是后续排查输入布局、权重排列、scale、字节序、激活函数、Concat 顺序或 Head 解析的重点位置。

### 3.2 脚本实现的主要功能

| 功能 | 实现内容 |
|---|---|
| 显式输入约束 | 必须提供 `--model`、`--image` 和 `--output-dir`；不会自行换成标定集第一张图片 |
| Gray1 预处理 | 按 `--preprocess-mode` 解码图片，执行 resize、`/255.0`、NCHW 和 FP16 转换 |
| 模型身份保持 | 只加载正式 ONNX；shape inference 和观察口扩展都发生在内存副本，不改写源文件 |
| FPGA 层映射 | 根据 Pose21 ONNX 节点名建立 `T32_Lxx_sxx` 计算层和 `T32_Lxx_rxx` 路由节点 |
| 多输入保留 | Add、Concat 等节点的所有运行时数据输入分别记录，不只保留最后一个输入 |
| Weight-only 识别 | Conv 只把第一个输入当作图像激活，不把 DequantizeLinear 产生的 INT8 权重副本误导出为激活 tensor |
| 中间结果捕获 | 临时将所需 tensor 暴露为 ONNX 输出，用 ONNX Runtime CPU 一次推理取得网络输入、各层中间值和最终 `output0` |
| tensor 去重 | 同一个 ONNX tensor 只写一个 BIN；不同层通过 manifest tensor ID 引用同一文件 |
| T32 物理转换 | 把 `[1,C,H,W]` 或 `[1,C,N]` 转为 FPGA 32-lane 布局，不足通道补零 |
| 自描述交付 | 生成原图、网络入口 BIN、逐层 BIN、`manifest.json`、`layers.csv`、README 和全目录 SHA-256 |
| 失败保护 | 先写同级 `.partial.<pid>`；拒绝覆盖非空目录，全部步骤通过后才原子发布正式目录 |

### 3.3 自动校验与发布门禁

脚本不是“把数组直接写盘”后就结束。每个 tensor 在发布前都要经过以下检查：

1. 转成小端 FP16 和 T32 物理布局。
2. 再从 T32 物理布局反解回原来的 ONNX 逻辑 shape。
3. 与 ONNX Runtime 返回的 FP16 tensor 逐元素比较。
4. 检查所有 padding lane 必须为零。
5. 检查 BIN 字节数必须与物理 shape 和 FP16 元素大小一致。
6. 检查 Pose21 主输出必须为 `output0=[1,31,34000]`。
7. 为每个文件生成 SHA-256，并生成整包 `SHA256SUMS`。

任何一项失败都会中止导出，不会把半成品目录当作正式结果。本次试验还额外执行了第二次完整导出，两次网络输入和 510 个 tensor 的哈希一致。

### 3.4 层号与 tensor 的关系

层号分为两类：

- `T32_Lxx_sxx`：卷积、SiLU、MaxPool、Resize 等 FPGA 计算层，保持既有 WT/BN 层号。
- `T32_Lxx_rxx`：Concat、Head 解码和最终输出等没有独立权重的路由节点。单独使用 `rxx`，避免插入路由节点后改变既有 `sxx` 权重层编号。

对于 Add、Concat 等多输入算子，所有数据输入都会分别登记。每个 ONNX tensor 只落盘一次；当多个层引用同一 tensor 时，通过 `manifest.json` 中的 tensor ID 复用，避免重复文件。

这里的“层”和“tensor”不是同一个概念：层是执行 Conv、Mul、Concat 等计算的节点或硬件阶段，tensor 是这些节点之间传递的多维数字数据。因此 182 条层/路由记录可以引用 510 个 tensor。导出包中的 `tensor_0000`、`tensor_0509` 是本工具分配的短 ID，`images`、`/model.0/conv/Conv_output_0`、`output0` 才是 ONNX 图里的实际 tensor 名称。

### 3.5 功能边界

该脚本不会执行以下工作：

- 不训练模型，也不重新量化或修改权重。
- 不生成新的正式 ONNX，不改变源 ONNX 的 graph、权重或输出合同。
- 不计算 462 张或 6,600 张数据集上的 Precision、Recall、F1 等整体精度。
- 不运行 FPGA 实机，也不自动读取和比较 FPGA 返回结果。
- 不生成或验证相机原始 `cam1280` 数据，不覆盖相机采集和图像前处理链路。
- 不替代正式量化 bundle 中的 WT/BN 权重包；本工具主要导出指定图片产生的网络输入和激活结果。

因此它适合回答“这张图片在软件参考模型的每一层应得到什么数值”，但不能单独证明“相机预处理正确”“FPGA 实机正确”或“整个数据集精度达标”。这些结论仍需分别使用 `cam1280` 测试向量、FPGA 回传数据和固定评估集完成验收。

### 4.3 捕获 ONNX 中间 tensor

工具对内存中的 ONNX 副本执行 shape inference，依据节点名称建立 FPGA 层映射，并把所需 tensor 暴露为临时输出。源 ONNX 文件没有被修改。

运行时使用：

```text
Python          3.12.12
ONNX Runtime    1.24.3
Provider        CPUExecutionProvider
```

一次推理后，工具收集各层输入输出及 Head 解码节点。Conv 只把第一个输入视为图像激活，不会把 weight-only 图中 DequantizeLinear 产生的权重错误地重复导出。

### 4.4 转换为 T32 物理布局

普通 NCHW 特征采用：

```text
[1,C,H,W] -> [ceil(C/32),H,W,32]
```

检测输出采用：

```text
[1,C,N] -> [N,ceil(C/32),32]
```

BIN 为小端 FP16。不足 32 通道的 lane 全部补零。每个 tensor 写完后都会从物理布局反解回逻辑布局，并与 ONNX Runtime 原值逐元素比较；不一致时本次导出失败，正式目录不会发布。

对网络入口而言，这一步产生的就是第 2.1.2 节所述 `source/network_input.bin`；它是第一层可直接消费的 T32 输入，而不是 `cam1280` 原始输入。

### A.2 对应口径

PPT 和逐层 trace 的粒度不同，不能只按行数直接比较：

- PPT 的一页 `CBS` 表示 `Conv2d + BatchNorm2d + SiLU`。导出所用 ONNX 已把 BatchNorm 参数折叠进 Conv，SiLU 在图中以内部 Sigmoid/Mul 实现，所以 trace 通常把一条 `Conv + Mul` 记为一个 `T32_Lxx_sxx`。
- PPT 的一页 C2f/C2 包含 `cv1`、多个 Bottleneck、Concat 和 `cv2`。trace 会把这些步骤展开成多条记录。
- PPT 用省略号表示重复 Bottleneck。CSV 仍逐个列出 `m.0`、`m.1` 等实际实例，并标为“模块级对应”。
- `T32_Lxx_rxx` 是 Concat、Head 解码等没有独立权重的路由记录。PPT 会画这些算子，但不会沿用 `sxx` 编号。
- CSV 中的“输出逻辑 shape”来自实际 ONNX Runtime 输出，不是 T32 补齐后的物理 shape。
