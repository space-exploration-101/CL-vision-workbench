## 1. 目标与范围

这里的 5090 指拟使用的 NVIDIA RTX 5090 GPU 主机；“互备”指一台不可用时由另一台接管，能力必须通过演练证明。

在 5090 上恢复预处理、训练、验证、PT 测试/推理、ONNX 评估、weight-only 量化、逐层导出、BIN 打包及 API/Web 服务。H200 保留现有环境，两个平台可从相同发布资产独立恢复，并在另一台不可用时接管新任务。

第一阶段采用人工接管和单写入端：每个任务只由一个平台执行、一个平台写入任务状态。正在运行的 GPU 任务不能靠复制 Docker 镜像无缝迁移；接管时从已验证 checkpoint 恢复，或在新任务目录重新运行。性能参数允许按设备调整，模型语义、数据身份和验收口径保持一致。

用户指定 `ubuntu22`，已完成 `$HOME/CL01_02` 初始化和资产/CPU 恢复；后续授权的固定原图回归、5090 GPU 验证、训练与续训烟测于 10.21 完成。H200 仅用于只读核对、读取归档及固定参考样本；未使用 H200 GPU，未修改全局配置、启动 API/Web 服务、切换服务或新增 NAS 发布。

先从 NAS 导入已验证镜像并核对完整内容身份，使用独立候选环境验证。10.20 已确认 H200/5090 显示的镜像 ID 分别为配置 digest/OCI manifest digest，须按[身份链](01_NAS备份与环境恢复.md#65-跨存储后端的镜像身份核验)核对，不直接比较两种 ID。镜像可导入不等于 GPU 兼容。RTX 5090 属于 Blackwell，必须现场读取实际 compute capability、`torch.cuda.get_arch_list()`、CUDA/cuDNN 版本并运行真实算子与反向；不能仅凭 `torch.cuda.is_available()` 或 `nvidia-smi` 成功判定通过。

若镜像内 PyTorch/CUDA 或扩展不支持目标 GPU，在独立候选工作区固定匹配的版本并重建新标签，同时回归本地 Ultralytics 8.3.98 Gray1 修改和 ORT 补丁。保留 10.16 镜像不覆盖；优先验证同一候选镜像能否同时运行 H200/5090，如必须分别构建，则记录两套镜像与同一算法发布版本的对应关系，并按第 1.1 节明确版本差异。具体升级版本需结合现场报错和官方兼容资料确定，本计划不预先承诺升级方案可用。

API Dockerfile 的 `ywang/yolo-gray1-quant:ultralytics-8.3.98-v6` 基础标签缺失，须在需要重建 API 前补齐明确来源的基础环境或建立可验证的新构建链。不得将训练镜像直接改名冒充量化基础镜像。已安装包版本清单不能替代 wheel/deb 离线包；升级依赖时保留完整下载包、传递依赖与哈希。

显存配置按现场容量与实测峰值制定。H200 历史 32 GiB 空闲门槛不能直接用于 5090；区分总显存、可用显存和 GiB/GB。先用 batch=1/2、小 worker 数、一次一个 GPU 任务测峰值，预留安全余量；训练如需梯度累积，明确有效 batch 和数值差异。保留 1280 单通道业务输入，不用降分辨率代替原流程验收。

## 6. 业务验收口径

1. **数据与模型身份**：冻结 PT 为 `622cff54db472b61c85db03648b36c119f030eacbd4cd87cf5d2dda67e69d6a7`，参考 ONNX 为 `031def2070a1c2183e62ce5713831bc69cd50dee3a22c10d0ffaff6580d91a02`。同一批图片、标签、划分与参数跨平台对比，禁止用新烟测随机权重替代正式模型。
2. **预处理**：固定原图验证 R 提取、net1280 单通道和 cam2000 packed-u12 格式；同实现确定性预处理要求文件或像素哈希一致。net1280 与相机 BIN 分别验收，不重复 resize/padding。
3. **训练与 PT**：核对实际张量 hook、首层通道、warmup、优化器步骤、checkpoint 与恢复；烟测只证明功能。正式训练复现需要另定随机种子、有效 batch 和指标标准，不要求不同 GPU 训练权重逐字节相同。
4. **PT/ONNX 测试**：先单图，再按已确认范围使用 eval462/500 张工程集；本迁移不安排 6,600 张全量 test。沿用 `conf=0.25`、NMS IoU=0.7 与既有匹配口径；运行前固定张量误差和精度差容限，记录最大/平均误差及指标差异。跨 GPU 浮点计算不预设逐位相同。500 张工程集存在训练 group 重叠，不能作为独立泛化结论。
5. **量化与打包**：执行 `pt_eval → quantize → onnx_eval → fpga_test_pack → fpga_input_roundtrip_eval → generate_bin → merge_bin → bundle`；检查 148 个 Conv 权重逐通道 QInt8、激活 FP16、无激活 QDQ，ORT 补丁实际加载路径正确。BIN 校验布局、shape、dtype、大小端、偏移和预期哈希；新导出的 ONNX 比较结构与数值，不能仅因文件哈希不同就断言失败。
6. **验收边界**：按用户要求不补跑 6,600 张全量回归，环境验收只覆盖实际已验证的样本和功能，不据此宣称正式全量精度通过。软件回环和逐层参考不等于 FPGA 实机通过，FPGA 数值闭环单列验收。
7. **服务与资源**：API/Web health、API ready、provider、GPU 所有权、并发限制、任务等待/失败/重试、结果下载都需通过。H200 10.16 备份时的 API NVML/ready 503 是既有待修复项；宣称 H200 可接管 GPU 量化前也必须复核并解决。

## 7. 双平台互备与发布约定

GitHub 保存源码与环境配置模板，NAS 保存不可变发布包；两台主机各保留至少一套已验证的本地镜像、源码、配置，以及接管所需的模型/数据。这样 NAS 短时不可达时仍能运行已落地的任务。NAS 是共享依赖，单靠两台 GPU 主机不能消除 NAS 单点故障；关键发布包应另有独立副本与恢复演练。

每个发布清单同时记录三仓 commit、H200/5090 镜像 ID、依赖与补丁版本、主机最低要求、PT/ONNX 和数据身份、部署挂载映射、验收结果、备份时间与来源平台。建议新增 `4-代码/<发布日期>_5090_docker_images/`，沿用 10.16 的每资产 README/SHA256SUMS/VERIFIED/records 布局；具体目录在执行发布时固定，不能覆盖原目录。

| 资产 | 同步/归档策略 | 接管要求 |
|---|---|---|
| 源码与配置模板 | 经验证的固定 commit，由 GitHub 或 NAS bundle 获取 | 使用匹配发布版本，不跟随浮动 main 自动更新 |
| 镜像与依赖 | 新发布一次，校验后分别落地两台；不复制 Docker daemon 数据目录 | 各自使用验证过的设备组合；保留上一版回滚镜像 |
| 模型与不可变数据 | 按版本与哈希从独立归档复制，只读使用 | 重新校验关键清单和模型身份 |
| 活动任务/checkpoint | 由任务拥有平台写入，按阶段原子归档；禁止双向覆盖正在写的目录 | 先确认原平台任务停止或已被隔离，再恢复/重跑；禁止两台重复抢同一任务 |
| 已完成结果 | output_data 按独立任务归档，验证后发布 | 分来源平台/任务 ID 保存；不并入系统镜像备份 |
| 凭据与服务地址 | 独立安全渠道维护；每台使用自己的配置 | 切换入口前校验权限和连通性，不把密码写入 Git/日志 |

建议初始目标：已验收发布资产接管前必须双机齐备；活动任务的最大数据损失由 checkpoint/阶段归档间隔决定，先以不超过 24 小时为规划目标。人工恢复服务的 RTO 先以 4 小时为规划目标。两项均是待实测目标，不是当前承诺；按数据量、网络与演练结果调整。

人工接管顺序：确认故障与原任务写入端隔离 → 选择最后完整发布/checkpoint → 核对目标 GPU 与资产 → 在新任务目录恢复或重跑 → 验证 health/ready 和结果 → 切换服务访问入口并记录任务映射。旧主机恢复后先保留只读对账，核对两边新结果再决定回切；禁止直接双向 rsync 活动状态或将整棵 output_data 互相覆盖。

### 9.4 怎样让镜像运行自己的代码

最重要的是分清两边的路径。例如：

```text
--mount type=bind,src=/home/ubuntu22/CL01_02/experiments,dst=/code,readonly
```

意思是把宿主的 `experiments/` 提供给容器，容器内用 `/code` 访问。Python 参数要写容器内路径，不能继续写宿主的 `/home/ubuntu22/...`。输入和代码通常只读挂载，输出目录单独可写挂载；这样容器结束后，结果仍保留在宿主机上。

假设已经把自己的脚本保存为 `experiments/my_task.py`，可以用以下 **CPU 模板**运行。这个文件只是举例，当前并没有替你创建：

```bash
RUN_ID="manual-$(date +%Y%m%d-%H%M%S)"
mkdir "$ROOT/runs/$RUN_ID"
docker run --name "$RUN_ID" --runtime runc --network none --read-only \
  --user "$(id -u):$(id -g)" --cpus 4 --memory 16g \
  --tmpfs /tmp:size=2g,mode=1777 \
  -e HOME=/tmp -e PYTHONDONTWRITEBYTECODE=1 \
  -e YOLO_CONFIG_DIR=/tmp/ultralytics -e MPLCONFIGDIR=/tmp/matplotlib \
  -e PYTHONPATH=/workspace/src/Yolo_fine/ultralytics \
  -e OMP_NUM_THREADS=4 -e MKL_NUM_THREADS=4 -e OPENBLAS_NUM_THREADS=4 \
  -e CUDA_VISIBLE_DEVICES=-1 -e NVIDIA_VISIBLE_DEVICES=void \
  --mount "type=bind,src=$ROOT/experiments,dst=/code,readonly" \
  --mount "type=bind,src=$ROOT/datasets,dst=/datasets,readonly" \
  --mount "type=bind,src=$ROOT/models,dst=/models,readonly" \
  --mount "type=bind,src=$ROOT/runs/$RUN_ID,dst=/output" \
  --entrypoint "$PYTHON" "$TRAIN_IMAGE" -B /code/my_task.py
```

脚本读取 `/datasets` 和 `/models`，把结果写到 `/output`。宿主结果就在 `runs/$RUN_ID/`。`--entrypoint` 指定真正要启动的解释器，避免误用镜像默认的服务启动命令。

要用 GPU，先按下一节检查资源，再把上述 `--runtime runc` 和两个隐藏 GPU 的环境变量去掉，增加 `--gpus "device=$GPU"`；脚本里同时设置 `device=0`。只传 `--gpus` 不会自动把代码里的 CPU 运算改成 GPU 运算。

**改宿主代码不一定影响容器。** 训练镜像默认使用镜像内 `/workspace/src/Yolo_fine/` 的代码。如果确实要测试宿主训练仓库的修改，需要额外把 `yolo-gray1-train/src/Yolo_fine` 只读挂到这个位置，并重新核对实际导入路径。平时复现现有环境不要随意换掉镜像内源码，更不要在容器里升级 Ultralytics。

### 9.5 训练和续训怎么跑

目前验证过的是 **8 张训练图、4 张验证图，一轮训练后再独立续训一轮**。下面使用同一份已验证包装脚本，但把结果写入全新的 `runs` 子目录，不覆盖原记录。

先连续观察 GPU，而不是只看一次利用率：

```bash
for attempt in 1 2 3 4 5; do
  nvidia-smi --id="$GPU" --query-gpu=uuid,memory.used,memory.free,utilization.gpu --format=csv
  nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
  sleep 2
done
```

同时用 `nvidia-smi` 查看进程列表，并用 `ps -o user,pid,etime,comm -p PID` 核对其中的实际 PID。确认无其他计算任务、至少 24,576 MiB 空闲后再开始；不要停止别人的进程。运行时另开终端持续观察，遇到外部计算竞争或剩余显存低于 2,048 MiB，应停止自己的容器。这里是手动调用示例，不包含原迁移启动器的自动资源保护。

```bash
RUN_ID="smoke-$(date +%Y%m%d-%H%M%S)"
mkdir "$ROOT/runs/$RUN_ID"

train_stage() {
  docker run --name "$RUN_ID-$1" --gpus "device=$GPU" \
    --network none --read-only --user "$(id -u):$(id -g)" \
    --cpus 8 --memory 24g --shm-size 4g --tmpfs /tmp:size=2g,mode=1777 \
    -e HOME=/tmp -e PYTHONDONTWRITEBYTECODE=1 \
    -e YOLO_CONFIG_DIR=/tmp/ultralytics -e MPLCONFIGDIR=/tmp/matplotlib \
    -e PYTHONPATH=/workspace/src/Yolo_fine/ultralytics \
    -e OMP_NUM_THREADS=4 -e MKL_NUM_THREADS=4 -e OPENBLAS_NUM_THREADS=4 \
    --mount "type=bind,src=$ROOT/datasets/pose21-gray1-1280-m-v1,dst=/dataset,readonly" \
    --mount "type=bind,src=$ROOT/runs/$RUN_ID,dst=/output" \
    --mount "type=bind,src=$ROOT/records/20261021-smoke/training_check_v2.py,dst=/code/train_smoke.py,readonly" \
    --entrypoint "$PYTHON" "$TRAIN_IMAGE" -B /code/train_smoke.py "$1"
}

train_stage train && train_stage resume
```

训练参数是 batch=2、workers=2、1280 单通道。包装保留了已验证的 AMP 初始 scale=1；它先生成独立小数据集，再从随机初始化训练，不是在微调 `models/best.pt`。两次都成功后，结果在：

```text
runs/<RUN_ID>/attempt2/
├── smoke-dataset/                 本次 8 train / 4 val
├── train-result.json              第一轮检查
├── resume-result.json             续训检查
└── training/smoke/
    ├── results.csv
    └── weights/                  epoch0.pt、epoch1.pt、best.pt、last.pt
```

正式训练主程序是镜像内的 `/workspace/src/Yolo_fine/train_yolov8x_p6_pose_gray1.py`，主要参数为 `--data`、`--epochs`、`--batch`、`--device`、`--workers`、`--project`、`--name` 和 `--resume`。正式训练不能只把上面的 epoch 数改大：需要选定训练范围、验证集和输出目录，并保留已验证的 AMP 适配。`best.pt/last.pt` 在训练完成后可能移除优化器状态；续训应选明确保存了优化器和 epoch 的 checkpoint，本轮验证的是 `epoch0.pt`。

仓库自带的 `docker/docker-compose.yml` 和 `run-gray1-training-smoke.sh` 还包含 H200 的用户、路径或资源假设，不作为这台 5090 的直接启动命令。`deployment/compose.cpu-check.yml` 也只是恢复检查，不是训练或服务部署文件。

### 9.6 PT 推理和批量测试

单图推理用冻结业务权重 `models/best.pt`，不要误用刚训练一轮的烟测权重。自己的 Python 脚本中，关键调用如下；可按第 9.4 节放进 `experiments/my_task.py`，先在 CPU 上运行：

```python
import cv2
from ultralytics import YOLO

pixels = cv2.imread('/datasets/cali/agaier_047_view_18.png', cv2.IMREAD_UNCHANGED)
assert pixels is not None and pixels.shape == (1280, 1280)
model = YOLO('/models/best.pt', task='pose')
results = model.predict(
    source=[pixels[..., None]], imgsz=1280,
    conf=0.25, iou=0.7, max_det=300,
    device='cpu', half=False, verbose=False,
)
print(results[0].boxes.data.cpu().tolist())
```

这里传的是显式单通道数组，不是图片路径。当前通用路径加载方式不能保证 Gray1 输入正确，不能简单改成 `source='某张图.png'`。切到 GPU 时，既要修改容器参数，也要把 `device='cpu'` 改为 `device=0`。

批量评估使用 API 镜像中的环境和平台脚本。两个原生入口的参数为：

```bash
/opt/ywang/yolo-runtime/bin/python pipeline/runner/01_pt_eval.py --job-dir /job
/opt/ywang/yolo-runtime/bin/python pipeline/runner/02_onnx_eval.py --job-dir /job --model /models/pose21_gray1_weight_only.onnx --input-mode direct --batch-size 1
```

这是**容器内命令**，需要在平台代码根目录运行。`/job` 必须是新任务目录，不能把数据集目录直接当作 job：

```text
job/
├── job_config.json               nc=21、imgsz=1280、conf=0.25、iou=0.7、passthrough
├── input/
│   ├── model.pt                  本任务模型
│   ├── test/images/              绑定 eval462 图片
│   ├── test/labels/              绑定对应标签
│   └── cali/                     需要量化时绑定 cal462
├── workspace/                    导出和量化中间结果
├── results/                      summary、逐图统计和可视化
└── logs/
```

还需把平台的 `pipeline`、`patches` 挂载到容器中实际使用的位置，不能只挂测试图片。完整挂载可查本轮 `records/20261021-eval462/pt-command.json` 与 `reference-command.json`。其中的 `/home/rs/wrs/onnxviewe/quantitize-platform` 是镜像内部保留的旧目录名，不是要在 5090 宿主上建立同名目录，也不是 SSH 跳板。

原生 ONNX 评估入口允许 provider 回退；本轮验证包装额外明确了 CPU provider 和 4/1 线程。若要按本轮结果复现，应保留这些设置，而不是只运行上述原生命令就认定配置相同。当前范围只用 eval462；不把 `datasets/.../images/test` 全部接进任务。

### 9.7 导出、量化与预处理

量化用 **API 镜像**，不是 Web 镜像，也不要求先把 Web 服务启动。当前实际路径是：

```text
models/best.pt
  → 独立可写副本 model.pt
  → PyTorch CUDA 导出 fp16.onnx
  → cal462 + ORT CPU MinMax + 本地补丁
  → weight_only.onnx
  → eval462 对比参考结果
```

导出器会在 `.pt` 旁边生成 `.onnx`，因此导出时使用任务目录内的副本，不要对只读挂载的 `models/best.pt` 直接导出。校准已经验证需要显式限制为 4/1 线程；原默认线程在容器 CPU 配额下出现严重节流。镜像里的 ORT 1.24.3 没有 CUDA provider，`--gpus all` 不会把它变成 GPU 版 ORT。

本轮实际调用保存在 `records/20261021-eval462/`：

| 文件 | 用途 |
|---|---|
| `workflow.py` | 固定模型和数据的 PT/ONNX 对比、FP16 导出 |
| `quantize_retry.py` | 四线程 CPU 校准、weight-only 检查和候选模型发布 |
| `launch.py`、`launch_retry.py` | 创建限额容器、记录命令、监控资源和退出状态 |
| `export-command.json`、`quantize-v2-command.json`、`new-command.json` | 本轮完整 Docker 参数，包含镜像、解释器与挂载 |

这些脚本带有本轮日期、固定目录和“不覆盖已有文件”的检查，**是执行记录，不是任意任务的通用启动器**。不要在原目录再次执行 `launch.py quantize`，也不要删除旧结果来绕过检查。新的量化任务需要另建目录、确认模型和校准数据，并调整包装中的路径；通用命令入口尚未整理完成。原 `pipeline/engine/quantitize.py` 还会继续做逐层比较，不能把它整段运行误认为只生成一个量化模型。

预处理使用独立的 CPU 镜像。查看其命令入口可以运行：

```bash
docker run --rm --runtime runc --network none --read-only \
  --cpus 2 --memory 2g --entrypoint python "$PREP_IMAGE" \
  -B -m grayprep.cli --help
```

新原图和标签只读挂载，生成结果写到独立输出目录。具体 profile 和数据构建参数见宿主 `yolo-gray1-data-pipeline/README.md`、`configs/net1280.yaml`、`configs/cam2000.yaml`；不要照搬 README 中 H200 的 32 workers 配置。现成 `datasets/` 不需要重新预处理。
