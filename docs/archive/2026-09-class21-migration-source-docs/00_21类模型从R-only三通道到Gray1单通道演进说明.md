## 1. 结论先行

模型演进包含两个彼此独立、但必须同时处理的变化：

1. 类别从 2 类扩展到 21 类，改变分类头、类别表、最终输出宽度和后处理偏移。
2. 网络输入从三通道 R-only 改为真正单通道 Gray1，改变模型第一层、ONNX 输入、量化校准输入和 FPGA 网络输入接口。

这不是简单地“把灰度图换一种存储方式”。以下两种张量即使肉眼显示相同，对网络也不是同一种输入：

```text
历史 R-only：[B,3,1280,1280]，R=gray，G=0，B=0
当前 Gray1：[B,1,1280,1280]，只有一个 gray 通道
```

2026-09-04 跑通的 21 类量化任务验证的是三通道 R-only 过渡模型和当时的平台链路。它证明了 21 类输出、R-only 输入回环和 FPGA 包装思路可以工作，但不能证明当前单通道 Gray1 权重已经完成量化或 FPGA 适配。

当前权威基线是：

```text
模型：21 类 Gray1 Pose，输入 [B,1,1280,1280]
权重：pose21_gray1_m_50e_20260917_113127/.../weights/best.pt
SHA-256：622cff54db472b61c85db03648b36c119f030eacbd4cd87cf5d2dda67e69d6a7
独立 test：6,600 张，运行 pose21_gray1_m_50e_test_eval_20260918_212142，PASS
量化状态：尚未开始当前 Gray1 权重的 FP16/QDQ/FPGA 流程
```

## 2. 三代模型与输入语义

| 阶段 | 模型与用途 | 类别 | 网络输入 | 灰度语义 | 当前定位 |
|---|---|---:|---|---|---|
| 历史基线 | 旧 YOLOv8x-Pose-P6 | 2 | `[B,3,1280,1280]` | 三通道接口接收 R-only，G/B 为 0 | 旧系统兼容和回归参考 |
| 过渡验证 | 2026-09-03/04 的 21 类模型 | 21 | `[B,3,1280,1280]` | R-only passthrough | 已跑通过量化和输入回环，但不是当前权重 |
| 当前正式基线 | 2026-09-17 的 21 类 Gray1 模型 | 21 | `[B,1,1280,1280]` | 真正单通道 | PT 训练和独立 test 已完成，待量化与 FPGA 验证 |

### 2.1 历史 2 类模型

历史 2 类模型仍是三通道彩图网络结构，但工程输入只在 R 通道放灰度值：

```text
R = gray
G = 0
B = 0
```

已记录的模型身份：

```text
文件大小：199,005,770 bytes
SHA-256：DF30B9FBC1CB5EB48E9EFADB53B2DFA6E52375255625438F8DC68EE27CC5C8E0
nc：2
类别：aituosha=0，moon=1
kpt_shape：[2,3]
```

本地归档：`docs/archive/2026-09-local-artifact-cleanup/model/yolov8x-pose-p6_2class-r-only_baseline_df30b9fb.pt`。

该表示法的优点是能复用三通道 YOLO、ONNX 和 FPGA 网络接口，缺点是 G/B 两路没有有效信息，第一层仍承担三通道存储、搬运和计算，并且极易被错误地改成 RGB-copy 或再次灰度化。

### 2.2 21 类三通道 R-only 过渡模型

2026-09-03 首次分析的 21 类 checkpoint 保持三通道结构，只把类别数扩展到 21：

```text
文件大小：199,053,642 bytes
SHA-256：94125BE741CC05BB2DF3F6D17D15FB07B182FB74011C2F5AB2669BE1C8F89E2F
nc：21
kpt_shape：[2,3]
```

相对旧 2 类模型，主干、颈部、四尺度检测头、bbox 分支和关键点分支不变。发生形状变化的是四个尺度的分类末端卷积：

```text
model.30.cv3.{0,1,2,3}.2.weight: [2,320,1,1] -> [21,320,1,1]
model.30.cv3.{0,1,2,3}.2.bias:   [2]           -> [21]
```

这一代模型用于证明平台从 2 类扩展到 21 类时，模型契约、NMS、输出解析和 FPGA 物理通道能够适配。它不是当前单通道正式权重。

当时的 checkpoint 训练参数还显示训练 `imgsz=1024`，而平台和 FPGA 按 `1280` 导出与评估。该差异不必然导致错误，但意味着 1280 下的精度只能作为新的部署实测基线，不能直接继承训练尺寸结论。这也是后来统一生成 net1280 数据、按 1280 训练和独立评估的重要背景。

### 2.3 当前 21 类单通道 Gray1 模型

当前权重从 Gray1 YAML 零初始化训练，模型第一层直接接收一个通道：

```text
路径：/data3/ywang/yolo-gray1-train/runs/pose21_gray1_m_50e_20260917_113127/experiments/pose21_gray1_m_50e_20260917_113127/weights/best.pt
字节数：199,108,106
SHA-256：622cff54db472b61c85db03648b36c119f030eacbd4cd87cf5d2dda67e69d6a7
输入：[B,1,1280,1280]
nc：21
kpt_shape：[2,3]
```

这一步消除了 G/B 空通道和三通道灰度语义歧义。收益主要发生在输入和第一层；不能把它表述成整个网络计算量缩小到三分之一，因为后续主干仍保持原有规模。

## 3. 为什么要做这些更改

### 3.1 从 2 类扩展到 21 类

旧模型只能识别 `aituosha` 和 `moon`。业务扩展后需要固定以下 21 类顺序：

```text
0 agaier       1 aipuha       2 aituosha    3 ansainusa
4 aoerhong     5 chapala      6 dibulong    7 didikaka
8 kanjialu     9 lupate      10 qinghai    11 rineiwa
12 sading     13 saersaer    14 saleikamei 15 taihu
16 taiwan     17 tana        18 tekesi     19 wennibeige
20 moon
```

旧模型中的 `aituosha=0、moon=1` 与新模型中的 `aituosha=2、moon=20` 不兼容。类别名相同不代表类别 ID 可以复用，因此模型、数据集、任务配置、后处理、FPGA 固件和上位机必须使用同一份有序类别表。

### 3.2 从 R-only 三通道改成真正 Gray1

早期选择 R-only 是为了少改三通道工具链，并保持与既有 FPGA 接口兼容。后续暴露出三个问题：

1. 通道语义脆弱。任何环节把 R-only 当普通 BGR/RGB 灰度图处理，都会改变亮度或通道分布。
2. G/B 通道始终为零，却仍占用输入带宽、buffer 和第一层计算。
3. “图片看起来是灰度”无法证明实际输入合同，三通道 R-only、三通道 RGB-copy 和单通道 Gray1 必须用张量 shape 与通道统计区分。

当前方案将训练、验证、独立 test 和后续量化统一到单通道 Gray1，减少隐式约定。代价是 ONNX、量化运行时和 FPGA 第一层必须明确支持 `ch=1`，不能直接复用三通道包。

### 3.3 统一几何预处理

部署链路确定为：

```text
原始约 2000x2000 图像
-> 缩放/降采样到 1000x1000
-> 四周各补 140 像素黑边
-> 1280x1280 网络输入
```

当前正式数据集已经离线生成真正单通道 `1280x1280 uint8` 图像。训练、val、test 和量化标定应使用同一几何与灰度语义，避免训练输入和部署输入分布不同。

`cam2000` 则是另一条接口：原始灰度图转换为 `2000x2000`、12-bit packed-u12 BIN。它用于相机/FPGA 输入协议和性能测试，不是 ONNX 标定数据，不能把 net1280 PNG 再转换一次后宣称等价于原始相机链路。

## 4. 类别扩展带来的输出变化

固定输入 `1280x1280`、stride 为 8/16/32/64 时，四个尺度候选数为：

```text
160x160 + 80x80 + 40x40 + 20x20 = 34,000
```

候选数不因类别数量变化。变化的是每个候选的类别通道：

| 项 | 旧 2 类 | 21 类 |
|---|---:|---:|
| 解码后 bbox | 4 | 4 |
| class | 2 | 21 |
| keypoint | 6 | 6 |
| 最终逻辑宽度 | 12 | 31 |
| 典型输出 | `[1,12,34000]` | `[1,31,34000]` |

21 类最终输出的逻辑布局是：

```text
ch0..3   bbox
ch4..24  21 个类别分数
ch25..30 两个关键点，共 6 个值
```

过渡任务的 FPGA 包把 31 个有效通道对齐为 32 个物理通道，`ch31` 是 padding，不能参与类别最大值、阈值、NMS 或关键点解析。

输入从三通道变成单通道不会改变上述检测头公式，但当前 Gray1 ONNX 尚未正式导出和验收。因此 `[1,1,1280,1280]` 输入、`[1,31,34000]` 输出、节点布局和物理 32 通道规则仍必须在当前权重的 FP16/QDQ 产物上重新确认。

## 5. 当时的分析与试验过程

### 5.1 静态结构审计

2026-09-03 先在隔离、无网络、无 GPU 的短生命周期环境中读取两个 checkpoint，确认网络拓扑相同，主要差异是分类头从 2 类增至 21 类。由此把工作重点从“重写量化器”收敛到以下接口：

- 模型、数据集和任务配置的 `task/nc/names/kpt_shape` 一致性；
- `imgsz=1280` 与 34,000 候选的单一事实来源；
- NMS、指标和网页报告不能回退到硬编码 2 类或 6 类；
- 分类权重的逻辑 21 通道到 FPGA 物理 32 通道映射；
- FPGA/host 的类别表、输出 offset、DMA 和 ABI 版本。

这一阶段形成了模型合同和分层验收思想，但当时很多内容只是计划，不代表已经实施。

### 5.2 第一次 21 类导出与量化探索

历史任务目录：

```text
/data3/ywang/quantitize-platform/data/output_data/20260903_1040_class21_best_fp16_eval/
```

该任务完成了 PT/ONNX 方向的探索，并确认 21 类最终输出为 `[1,31,34000]`。当时 FPGA 权重 BIN、合并和打包尚未完成，因此它只是一段中间证据。

### 5.3 R-only 输入回环故障

任务 `20260903_190838_test_21_class_pipeline_02` 中，direct ONNX F1 为 `0.9420`，但 `fpga_input_roundtrip_eval` F1 只有 `0.5872`。

故障原因不是网络结构，而是软件回环错误：

```text
R-only PNG
-> 错误执行 BGR2GRAY
-> 有效 R 亮度被压到约 0.299 倍
-> side_view 又保存为三通道同值灰度
-> 回环输入不再等于 direct ONNX 输入
```

修复原则是让任务配置决定预处理：passthrough R-only 输入直接取有效 R 通道，BIN 解码后的 side view 也恢复为 `R=gray,G=B=0`，而不是 RGB-copy。

这个故障带来的长期结论是：输入合同必须逐阶段验证，不能以“肉眼看起来相同”替代通道级对齐。

## 6. 三通道 R-only 与单通道 Gray1 的工程差异

| 环节 | 历史/过渡 R-only | 当前 Gray1 | 必须采取的动作 |
|---|---|---|---|
| 图片语义 | R 有效，G/B 为 0 | 单通道 uint8 | 禁止隐式 RGB-copy 或 BGR2GRAY |
| PT 输入 | `[B,3,1280,1280]` | `[B,1,1280,1280]` | Predictor/Validator 均按模型 `ch` 预热 |
| 第一层卷积 | 3 个输入通道 | 1 个输入通道 | ONNX、量化和 FPGA 权重必须重新生成 |
| 标定数据 | 三通道 R-only PNG | 单通道 net1280 PNG | 使用 train split 独立选择，不复用旧标定集 |
| ONNX 输入 | `[1,3,1280,1280]` | 预期 `[1,1,1280,1280]` | 对当前 FP16/QDQ 模型做结构探针 |
| 检测头 | 21 类时逻辑宽度 31 | 预期仍为 31 | 用实际 ONNX 证明，不能只套公式 |
| FPGA 输入 | 构造 R/G/B 三通道 | 应直接消费单通道网络输入 | 确认硬件第一层、buffer、DMA 和打包格式 |
| 后处理 | 21 类 offset 已探索 | 类别/关键点 offset 原理不变 | 重新对齐当前 ONNX/FPGA 输出 |
| 历史量化结果 | 已有 84 张对齐结果 | 尚未量化 | 不得跨模型引用精度结论 |

当前训练镜像曾因 Predictor 预热写死 3 通道而无法直接推理。修复包含：

- 预热通道取模型元数据或 YAML 的 `ch`；
- LetterBox 挤掉 `HxWx1` 末维时补回通道维；
- 仅三通道输入执行 BGR 到 RGB 翻转，单通道只做 BHWC 到 BCHW。

这说明平台所有入口都必须显式接受输入通道合同，不能只修改模型第一层后继续依赖三通道预处理。

## 7. 保留下来的正确方法

虽然旧 Agent 文档不再作为执行说明，其中以下方法仍然有效。

### 7.1 模型合同是唯一事实来源

至少固定并交叉检查：

```yaml
task: pose
nc: 21
class_names: exact ordered map 0..20
kpt_shape: [2, 3]
input_channels: 1
input_size: 1280
input_semantics: gray1
strides: [8, 16, 32, 64]
num_candidates: 34000
```

模型、数据集、任务配置、ONNX、量化产物和 FPGA manifest 任一不一致都应在运行前硬失败。

### 7.2 分层验证，不跨层归因

执行顺序应保持：

```text
PT 基线
-> FP16 ONNX parity
-> QDQ ONNX 量化损失
-> 逐层权重/BIN roundtrip
-> FPGA 输入 roundtrip
-> FPGA 实机输出
-> 旧 2 类 golden regression
```

每一层使用同一批样本和同一后处理口径比较。上一层未对齐时，不进入下一层，也不通过调阈值掩盖输入或 ABI 错误。

### 7.3 独立 test 的固定匹配口径

当前 PT test 使用：

```text
conf=0.25
NMS IoU=0.7
同类匹配 IoU>=0.5
按预测置信度贪心一对一匹配
关键点置信度阈值=0.5
```

中心和关键点像素误差只对成功匹配实例计算；FP/FN 必须独立报告，不能计为 `0 px`。量化后完整 6,600 张回归必须复用这一口径。

### 7.4 FPGA/host 仍需核对的接口

- 有效类别数必须是 21，不能把物理 padding 通道当类别；
- bbox、class、keypoint 的 offset 必须来自当前产物合同；
- 输出 buffer、DMA 长度、stride 和量化 dtype 必须与当前 Gray1 包一致；
- 类别 ID 始终限定在 0..20，并携带同一类别表；
- checkpoint、ONNX、权重 BIN、BN BIN 和 ABI 版本应写入同一个 manifest；
- 旧 2 类、新 21 类三通道和当前 21 类单通道包必须能够被加载端拒绝交叉混用。

### 7.5 业务后处理假设要单独验收

早期方案提出“20 个地标互斥、moon 可与一个地标共存”，建议在普通 NMS 后增加业务过滤。该规则不属于模型张量 ABI，也不能因历史文档写过就视为已实现或已获业务确认。若继续采用，应单独确认规则、实现位置和测试用例。

### 7.6 兼容性必须包含负向门禁

旧 Agent 规格中最值得保留的是“错误组合必须在计算开始前失败”，而不只是验证正确组合能够运行。当前 Gray1 流程至少应覆盖：

| 场景 | 预期结果 |
|---|---|
| 21 类模型 + 完全一致的 21 类数据合同 | 允许创建并执行 |
| 模型与数据集的 `nc` 不一致 | GPU/量化前硬失败 |
| `nc=21` 但类别名称被重排 | 硬失败 |
| label id 小于 0 或大于 20 | 硬失败 |
| 任一类别零覆盖 | 失败，或要求显式批准的豁免记录 |
| 输入通道、尺寸或语义与 Gray1 ABI 不一致 | 硬失败 |
| 逻辑 21 类映射到物理 32 通道 | 只允许显式 padding，并验证 21..31 不参与类别计算 |
| 逻辑类别数超过物理容量 | 硬失败，禁止静默截断 |
| checkpoint、类别表、ABI 或 BIN 跨版本混用 | 加载端拒绝 |
| 历史 2 类 golden task | 保持原有行为，作为兼容回归 |

checkpoint 元数据检查也必须维持隔离边界：不在常驻 API/Web 进程中反序列化不可信 `.pt`。检查应放在无网络、无 GPU、只读根文件系统、带 CPU/内存/超时限制的短生命周期容器或进程中；`weights_only=True` 不能代替这一隔离措施。

## 8. 历史计划中未执行或已过期的内容

以下内容保留作溯源，不应直接执行：

1. `epoch75_strip.pt` 的 R-only 独立评估计划没有成为当前正式基线。
2. 该计划曾指定 `/data3/ywang/evaluations/<RUN_ID>/` 和旧 NAS 项目目录；当前评估实际运行目录、NAS 位置和归档规则以独立 test 报告及当前 RUNBOOK 为准。
3. 旧规格中的 `input_channels=3`、`grayscale_r_channel`、`passthrough` 和 RGB/BGR 转换逻辑不适用于当前 Gray1 输入。
4. 旧任务中的 791 张标定集、84 张测试集、权重哈希和 BIN 大小只属于过渡模型。
5. 旧文档对 `L43_bin_process.py` 来源不明、21 到 32 通道填充值和 FPGA ABI 的疑问，后来只在过渡任务产物上得到部分答案；当前 Gray1 包仍需重新给出证据。
6. 旧文档中的平台代码行号、默认 `nc=2/6` 和文件状态来自 2026-09-03 快照，不能代替当前代码审计。
7. 顶层旧目录曾保存 2026-09-09 Step 15 小规模 Gray1 实验的 `best.pt`（199,108,234 bytes，SHA-256 `292cb13d...f1f527f`）。它不是当前正式权重；其原 H200 实验路径在 2026-09-18 复核时已不存在，因此唯一可见的本地副本移入 `docs/archive/2026-09-gray1-step15-checkpoint/`，仅供历史复核。

旧 R-only 评估计划留下的正确审计顺序仍可复用：先冻结输入合同和参数，再做数据/权重门禁、GPU 持续采样、冒烟、全量推理、误差统计，最后归档；但执行命令和路径必须从当前文档与现场重新生成。

当时还讨论过以下优化方向，它们被延后而不是被验证为无效：

- 将灰度复制到 RGB 三通道：更接近常规 RGB 预训练输入，但仍保留三通道冗余，并要求重新训练和全链路验证；
- 删除 stride 8 的 25,600 个小尺度候选：可能减少输出搬运和 NMS 成本，但必须先证明业务目标尺寸不会造成召回损失；
- 在 FPGA 端提前做阈值或 top-k：可能减少约 `34000 x 32 x 2` 字节的输出搬运，但会增加硬件逻辑和软硬件一致性风险；
- 将 NMS 全部放入 FPGA：NMS 包含排序、动态分支和不规则访存，早期判断仍倾向保留在 CPU/ARM 侧，除非性能实测证明它是主要瓶颈。

当前阶段继续遵循“先保证输入和结果正确，再验证量化与 ABI，最后优化性能”的顺序。

## 9. 当前应如何继续

当前下一阶段不是复跑旧三通道任务，而是针对冻结 Gray1 `best.pt` 建立新的量化任务：

1. 从 train 选择 462 张单通道标定图，并保存确定性 selection manifest。
2. 从 test 选择 462 张快速评估集，先做 PT 双路径对齐。
3. 导出并检查 FP16 ONNX，确认输入 `[1,1,1280,1280]` 和实际输出 ABI。
4. 执行静态 QDQ 量化，比较 PT、FP16 和 QDQ 的同集结果。
5. 快速门禁通过后，对完整 6,600 张 test 做 FP16/QDQ 回归。
6. 单独验证 cam2000 原始输入协议与性能，不把它当作标定输入。
7. 软件量化通过后，再决定如何生成当前 Gray1 FPGA 包和修改第一层硬件接口。

具体数量、阈值、目录、代码和镜像身份以 [21 类 Gray1 模型量化与 cam2000 性能测试计划](21类灰度图模型量化与cam2000性能测试计划.md) 为准。
