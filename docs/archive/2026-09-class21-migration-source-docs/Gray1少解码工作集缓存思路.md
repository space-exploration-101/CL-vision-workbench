# Gray1 少解码工作集缓存思路

> 更新日期：2026-09-19  
> 状态：**思路备忘，未实施、未授权。** 不改变当前正式 PNG 真源，也不插入正在进行的 PT→FP16→QDQ 任务。  
> 来源：2026-09-19 量化任务运行期间关于「PNG 解码到 numpy 很吃 CPU，能否换成后续读取更便宜的格式」的讨论。  
> 适用：后续训练、推理测试、量化标定的 I/O 优化评估。不是当前量化验收条件。

## 0. 先用白话说清楚

训练、PT 评估、量化标定真正要的，不是「一张 PNG 文件」，而是内存里的一张数字表：每个像素一个 0–255 的整数，尺寸固定为 `1280×1280`，只有一个灰度通道。这份数字表就是常说的 **numpy 数组** / **张量**。

PNG 是一种 **压缩容器**：为了省磁盘，把这张数字表打成较小的文件。每次要用像素时，程序必须：

```text
读磁盘上的 PNG
  → 解压缩（CPU 做大量计算，这一步叫解码）
  → 得到 1280×1280 的 uint8 像素
  → 再按任务需要变成网络输入（例如除以 255、改成 float16、排成 NCHW）
```

「解码」不是打开图片给人看，而是把压缩文件还原成数字。你们的 Gray1 图已经是定死尺寸的单通道图，PNG 压缩比仍然有意义（整份正式集约 15 GB；若存成未压缩像素大约 44 GB），所以解码不是免费的。

量化一次只读 462 张标定图，解码通常不是最长的一段（当前这次慢，主因是 GPU 争用和 Entropy 标定本身）。真正会反复付钱的是 **训练**：每个 epoch 都要把上万张图再解一遍。所以这份备忘把「少解码缓存」记下来，供以后做性能优化时评估，而不是现在改数据合同。

常用词对照：

| 说法 | 含义 |
|---|---|
| `uint8` | 每个像素用 1 个字节，取值 0–255，和 PNG 里的灰度值一致 |
| `float16` / `fp16` | 半精度小数，量化标定和 ONNX 常用；通常还要把 0–255 除以 255 |
| `NCHW` | 数组排布：批次、通道、高、宽。网络输入是 `[N,1,1280,1280]` |
| `mmap` / 内存映射 | 把一个大文件当成内存来读，操作系统用 page cache 加速重复访问 |
| 真源 | 以谁的哈希和像素为准。当前真源是正式 Gray1 PNG |
| 派生缓存 | 从真源生成的加速副本，丢了可以重做，不能反过来覆盖真源 |

## 1. 当前事实（不要从这份备忘推断成已上线）

正式派生数据：

```text
/data3/ywang/yolo-gray1-datasets/pose21-gray1-1280-m-v1
```

合同：`1280×1280`、`uint8`、真正单通道 Gray1 PNG。训练、val、独立 test、量化标定都应使用同一几何和灰度语义。不得向该目录内新增 calibration 目录，也不得用新格式原地替换 PNG。

量化标定当前路径仍是：

```text
PNG → 解码成数组 → 预处理（本轮 passthrough）→ float16 NCHW → ORT Entropy
```

H200 内存约 1 TiB。整份 M 规模正式集约 26,794 张；若存成未压缩 `uint8`，大约：

```text
26794 × 1280 × 1280 ≈ 43.9 GiB
```

整份工作集可以放进内存。这是后面「不换格式、先预加载」能成立的原因。

## 2. 三种数据合同必须分开

不要发明「一个 BIN 打天下」。三条链路要的像素几何和位宽不同：

| 用途 | 现在用什么 | 尺寸 / 位宽 | 能不能互相替代 |
|---|---|---|---|
| 训练、PT、量化、软件评估 | net1280 Gray1 PNG | `1280×1280` uint8 单通道 | 这是网络输入合同 |
| 相机 / FPGA 输入协议 | cam2000 packed-u12 BIN | `2000×2000`、12-bit、行 stride 4096 | **不能**当量化标定或训练图 |
| 人看、抽查、哈希、归档 | PNG + manifest + `VERIFIED` | 可视、可逐文件哈希 | 不可视大文件不能当唯一真源 |

cam2000 每个 BIN 为 8,192,000 字节，行尾补零，无文件头尾。它证明「为特定 ABI 做专用二进制」这条路你们已经走过；那是相机协议，不是 net1280 的少解码缓存。

## 3. 建议的分层（若以后做）

```text
PNG（归档真源，不改）
  └─ uint8 少解码工作集（训练、PT、像素评估优先读这里）
       └─ 可选 fp16 NCHW 缓存（仅 ORT 标定，不算像素真源）
cam2000 BIN（另一条 ABI，不进上面这条）
```

原则：

1. PNG 继续当 `VERIFIED` 真源；工作集按 PNG 的 SHA-256 索引。
2. 缓存对不上 PNG 哈希就拒绝使用，不允许「缓存漂了还继续训」。
3. 缓存丢失可以重生成；不能把缓存写回正式数据集。
4. 训练和像素评估以 `uint8` 为准；不要把已经 `/255` 的 fp16 当成训练输入。

## 4. 可选思路（按「以后真可能有用」排序）

这些都是候选，不是选型结论。上线前必须有对照实验：同一批 PNG 哈希、同一模型、解码/训练/标定 wall time、峰值 RSS、以及逐像素或逐图指标一致。

### 4.1 每张图一个未压缩 `.gray`（或 `.pgm`）

文件内容就是 `1280×1280` 个字节，一共 1,638,400 字节，没有 PNG 那种解压缩。

读取接近：

```text
np.fromfile(path, dtype=np.uint8).reshape(1, 1280, 1280)
```

优点：概念简单，和现有「一图一文件 + 一标签」布局兼容。  
缺点：Ultralytics 默认仍读 PNG/JPG，训练要接一层 Dataset；磁盘大约从 15 GB 涨到 44 GB。

### 4.2 按 split 做成一块 mmap

例如 `train.uint8.n1hw`，形状 `[N,1,1280,1280]`，外加 `index.json`（文件名、group、标签偏移、源 PNG 哈希）。

标定和顺序扫描最合适。H200 第一次读完后，后续 epoch 多半走 page cache，接近内存拷贝。  
缺点：改一张图要重写整块；很多 DataLoader worker 同时随机打同一文件时，要限制并发和预读策略。

### 4.3 只给量化做 fp16 NCHW 缓存

ORT Entropy 要的是 `[1,1,1280,1280] float16`。可以把「解码 + `/255` + 排成 NCHW」一次性做好。标定阶段几乎只剩 `np.load`。

这份缓存 **不能** 当训练真源：增强、可视化、像素哈希、与 PNG 对拍都在 uint8 上。允许同时存在「像素缓存」和「网络输入缓存」，但要在 manifest 里写清各自用途。

### 4.4 不换格式，换「何时解码」

H200 内存够把整个 uint8 工作集 preload 到共享内存或 `/dev/shm`。grayprep 产出 PNG 之后做一次解码，训练和量化只读已经展开的像素。

这往往比发明第四种文件格式更便宜，也更少改 YOLO / 量化 DataReader。grayprep 历史性能实验已经表明：OpenCV 线程数会明显改变 PNG 吞吐，说明解码开销是真的，但不等于必须换容器。

### 4.5 QOI / 未压缩 TIFF / BMP

比 raw 略省空间，解码仍接近内存拷贝。对已经定死尺寸的灰度图，收益通常小于直接 `.gray`，而 loader 生态并不比 raw 更好。可以作为对照实验，不作为默认方向。

## 5. 不太值得的方向

- **JPEG / WebP 有损**：Gray1 合同是精确 uint8。量化标定不能再引入压缩误差。
- **用 cam2000 BIN 训练或量化**：几何 2000、12-bit、行尾补零，和 `[1,1,1280,1280]` 不是一回事。
- **LMDB / TFRecord / HDF5 作为第一选择**：2.6 万张定长灰度图过重；随机读、跨机复制、恢复都更烦，还要写一套新 loader。
- **在正式 PNG 目录里原地替换**：破坏现有 `VERIFIED`、`SHA256SUMS` 和人工抽查。

## 6. 和当前量化任务的关系

本轮 21 类 Gray1 量化仍使用 PNG 标定集 `pose21_gray1_50e_cal462_v1` 和评估集 `pose21_gray1_50e_eval462_v2`。

不要用「解码优化」解释当前 `quantize` 变慢：

- 历史约 12 分钟，指的是 9 月 2 日两月坑 CUDA **整条八步**（标定 500、测试 840），其中量化一步约 3.5–4.5 分钟。
- 9 月 4 日 21 类 R-only CUDA 量化一步约 7 分钟（791 张标定、84 张测试）。
- 本轮计划给 462 张 CPU QDQ 标定预留的是 90–120 分钟。
- 2026-09-19 这次量化与 `noah` 的进程共享 GPU3，标定推理会变慢。

解码优化是后续训练和反复评估的杠杆，不是本轮量化的门禁，也不是当前任务的修复项。

## 7. 若以后要做，建议的第一刀

尚未授权。真要启动时，最小切口应是：

1. 只读正式 PNG，生成派生 `.gray`（或 mmap）到 **独立目录**，不写回 `pose21-gray1-1280-m-v1`。
2. 大文件先写 `.partial`，校验后再原子改名。
3. manifest 同时记录 PNG SHA-256 和缓存 SHA-256。
4. 量化 DataReader / 训练 Dataset 优先读缓存；哈希不一致则失败，禁止静默回退到「可能漂了的缓存」。
5. 固定一小批图做 A/B：PNG 路径 vs 缓存路径，逐像素必须一致，再比 wall time。
6. YOLO 默认 loader 未改之前，不能宣称「训练已经用上新格式」。

对照实验至少要分开报告：解码时间、预处理时间、GPU 等待时间、标定/训练逐步耗时。不要只看端到端，否则会把 GPU 争用误记成解码问题。
